Where an agent workforce can take over work between scan and floor plan

The question: which steps of the pipeline — sorting point clouds into rooms, puzzling rooms into storeys, modelling boundaries, walls, doors and windows, then delivering floor plan and room book — can an agent do, or do most of, so that people only review. This page says what a person does today at every step, what already exists in code, and lists the candidates ranked by how sure I am they work with what we have.

How it was checked: the LumoCad manuals and code, the api and lumoplan repos, the lumoflow-skills agent runtime spec, and Notion (the Revit workflow, the Q3 "Automation-first" and "halve post-processing time" key results, the Q4 End2End workflow). Code paths are given so a developer can verify; everyone else can skip them.

In short

  • The solvers mostly exist. Room solver, boundary fit v2, boundary finetuning, walls from boundaries, plan extraction with 52 QA warning codes, room book schedule. All of them are pure TypeScript running on the browser main thread or in a web worker. Nothing runs them headless, so every run waits for a person to click.
  • Still fully manual: the room puzzle (stage 2), storey stacking, the whole opening chain (draw marks → merge → link → place on wall → type → features), wall-type classification, dimensions (by decision), room naming and numbering, flat grouping, QC checklist ticking, catalogue mapping, stage completion in LumoPlan.
  • The leverage is not more solvers. It is (a) running the existing solvers headless when data lands, (b) agents that triage the diagnostics those solvers already emit, (c) language and vision agents on the judgement steps.
  • Queue time is about half of every phase. A building sits a median of 8 workdays in pending3DPostprocessing. Process agents (readiness gates, triage, routing) shorten delivery as much as modelling agents shorten effort.
  • A runtime already exists. lumoflow-skills/lumoagent-job-flow defines an agentic serverless job (MCP tools, mandatory artifact state machine, Bruno trigger) with two precedents, floor-plan-audit and qa-agent. The API supports organisation API keys, which keep agent writes distinguishable from human writes.

The Revit workflow, for comparison

Notion's "Revit Workflow From Start To End" (Axel, Timothy, Elyes) has four phases: premodelling (template, load clouds, storey heights from stair clouds, align floors with reference planes, link models), 3D post (external walls, stairs, stairwell walls, roof, internal walls, curtain walls, windows, doors, room tags, in-place families, slabs), 2D post (view templates, views) and sheets. Every step page is a screen recording. LumoCad already has a tool for every step except in-place families and curtain walls, so "everything in LumoCad" is a coverage question for those two and a speed question for the rest.

Tier 1 — build first

High confidence: the hooks exist in code today and the leverage is large. Kind: batch deterministic job, no language model needed · LLM language or judgement over structured data · vision image model.

  1. T1-1

    Readiness & QA report agent

    stage 6 + QCbatchLLM

    Nightly or before hand-in, run the plan extraction headless per building, emit the warnings report, map each code to the QC-2D checklist item it proves or disproves (wall join gaps ↔ "wall joins clean", unreferenced sections ↔ "section cuts referenced", windows outside the cut plane ↔ "windows cut", room codes ↔ "room labels", no manual dimensions ↔ "dimensions"), route each code to an owner and draft the hand-in note.

    Why it works nowExtraction is pure; 52 codes are already defined in constants/floorplanWarnings.ts; tests already run the whole pipeline with fake actors.
    PrerequisiteP1, the headless model loader.
  2. T1-2

    Openings proposer: masks → draft observations

    stage 5batch

    Run the mask-to-observation conversion on every new panorama instead of by manual task, write the results as draft observations under an agent identity, and let the existing cleanup, merge and link screens be the human review step.

    Why it works nowMasks with scores exist for every panorama; the PROCESS_OBSERVATION worker exists; the review UI exists.
    PrerequisiteP2 agent identity; confirm with Piotr which identity the worker writes with today.
  3. T1-3

    Observation ↔ capture-opening matcher

    stage 5batch

    Merged observations have a position but no reliable dimensions; detached capture openings have dimensions and the two rooms but no position. Solve the assignment over shared rooms, width difference and door-vs-window, write the link, let a person confirm.

    Why it works nowBoth data sets exist; today a person picks the match per door in a modal.
    PrerequisiteT1-2.
  4. T1-4

    Autosort on ingest + triage

    stage 1batchLLM

    Run the room solver in Node per room when scans land, with a retry ladder (default profile → high-recall profile → skip-IMU → creation-order → 3D reconstruction). Rank rooms by the metrics the solver already reports (tuning score, held-out NCC and IoU, connected fraction) and send people only to the failing rooms with the diagnostic reason.

    Why it works nowThe engine is pure and already runs in a worker; the summary JSON exists; reconstruction is already queued through POST /task.
    PrerequisiteP3 pose write-back. Today the only external path is uploading a v4 sorting backup and a person clicking Restore.
  5. T1-5

    Benchmark from hand-in backups

    stage 1batch

    Every hand-in uploads a human-verified v4 layout. That is a free labelled dataset: compute absolute pose error per room, run offline hyper-parameter optimisation, and derive auto-accept thresholds that T1-4 can defend.

    Why it works nowThe docs ask for exactly this ("absolute pose error should become the main benchmark") and no dataset is checked in.
  6. T1-6

    Reference-plane proposer

    stage 3batch

    Detect oblique wall families from the fit-line angle histogram and propose reference planes before the boundary fit runs. Today a missing plane silently drops those walls and the person has to notice.

    Why it works nowgenerateBuildingMainGuidelines() already clusters directions; chain it.
  7. T1-7

    Issue-worklist agent

    stages 3 + 4LLM

    Consume the typed diagnostics the tools already produce (fit reasons, reconciliation issue codes, rounding and alignment skips, wall residual JSON, advisory near-collinear and non-parallel markers) and emit fix proposals that call existing edge actions (Align, Match angle, Make parallel). Include a batch "match all red and orange thickness pairs to the captured thickness" as one undo step.

    Why it works nowEvery diagnostic is typed and sits in a store; the per-pair solver exists, only orchestration is missing.
  8. T1-8

    Wall-type classifier

    stage 4LLM

    Cluster wall thickness per building, snap each cluster to the nearest preset (365, 425, 300, 240, 175, 115; drywall 75, 100, 125, 150), weight by captured door thickness and the external/internal flag, propose assignments, person approves.

    Why it works nowThis is the only pure-judgement step left in stage 4; the organizer already groups by rounded thickness but applies nothing.
  9. T1-9

    Opening-type organizer auto-apply

    stage 5batch

    Accept the suggested groups, name types by convention, bind them; a separate pass merges duplicate types.

    Why it works nowDeterministic and reversible through undo and type unbind.
  10. T1-10

    Area reconciliation

    stage 7batch

    Diff the platform Raumbuch, the LumoCad Room Book and the plan tags per room; flag every delta (roof band, stair deduction, manual overrides, stored BGF fallback).

    Why it works nowBoth exports are node-able; today they can print different areas for the same room without anyone noticing.
  11. T1-11

    Catalogue mapper

    stage 7LLM

    Map unmapped checklist values to the German catalogue entries. Today they only reach the browser console.

    Why it works nowClosed vocabulary, a classic language-model task with a human spot check.
  12. T1-12

    Preprocessing progress & triage agent

    processLLM

    Daily per building: compute the four preprocessing stages with the existing projected queries, raise the planned flags (boundaries requested but none drawn, sorted but no observations, automation-only observations), write a "why was this shared, what to do next" note, nag or bulk-unshare stale shares.

    Why it works nowThe queries exist in LumoPlan and are proven against production; the gap is synthesis and routing. It answers the named pain "nobody says why a building was shared".
  13. T1-13

    Processing-pipeline health agent

    APIbatch

    For recent telemetry, check that derived files exist (panorama → tags and vanish points; rotlidar → point-cloud fitting and .rcs; room → 3D package), re-dispatch missing ones through POST /task, summarise failed tasks.

    Why it works nowThere are no completion callbacks; rotlidar send errors are swallowed; the 3D package and observations are manual-only. Today a person has to notice.

Not worth it now

  • Dimensions. Rio's decision (M6): stop automating references; a person places and corrects them anyway.
  • Stairs from the legacy staircase measurement. No input path exists and the geometry is complex.
  • Assignment and routing. Deterministic rules already exist; a language model adds little.
  • Stage-overdue scanner. The rules are trivial and it is blocked on LumoPlan service auth.

Suggested first three pilots

1 · Readiness & QA report

T1-1 + T1-12. Read-only, zero write risk, immediate value for coordinators, and it forces the headless loader (P1) into existence.

2 · Openings proposer + matcher

T1-2 + T1-3. The longest manual chain per room; mask data and the review screens already exist; needs only the agent identity (P2).

3 · Autosort on ingest + benchmark

T1-4 + T1-5. Attacks the preprocessing queue; the benchmark from hand-in backups makes auto-accept thresholds defensible.
