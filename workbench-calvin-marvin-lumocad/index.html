One loop, four layers: where your work with Workbench fits next to Calvin, Marvin and LumoCad

After the meeting with Piotr and Arne on 6 November, the picture is clearer. Workbench is where you talk to a coding agent. Calvin is the cable that lets that agent see and change a live LumoCad building while developing. Marvin is the chat that architects use. LumoCad is the platform they all end up in.

The short version

Two moments in time. Keep them apart in your head and most of the confusion goes away.

BUILD TIME: you, Piotr and Arne, on your own machines

You open a chat in Workbench, pick a gap (wall types, doors, windows), and a coding agent changes LumoCad's code. Once Piotr's harness is merged, Calvin lets that agent try its change on a live building and see the result right away. A golden set of known-good buildings says whether the result is actually better.

USE TIME: an architect, in the real app

The architect types to Marvin inside LumoCad. Marvin proposes a change, the architect presses Approve, and the change goes through LumoCad's own editing path, so Undo works. Marvin never touches code, and Calvin does not exist here at all.

One correction from the meeting. We believed our branch (marvin/native-apply-milton) already contained Piotr's harness. It does not: only origin/development was merged into it. Piotr has not merged his harness yet, and he will do it himself. Until he does, nothing on this page about Calvin can be tried by you.

Workbench

Your desk · yours alone

A local chat window for coding agents, with Work Hub for tickets, meeting notes and OKRs. Edits ask first and show the real diff. Each chat can use its own copy of the code.

Runs: on your Mac.
Ships: never.

Calvin

Connector · Piotr's branch

Gives a coding agent live, structured access to LumoCad's building state, skipping the browser screen and the database. Codex plus Calvin together is the full harness.

Runs: local dev server only.
Ships: can go to main early, it has no production surface.

Marvin

Architect chat · Arne's service

A chat inside LumoCad. About 84 tools to read, plan and propose. Cannot touch code. Every change needs a human Approve.

Runs: browser pane + Go service + MongoDB.
Ships: soon, behind an experimental flag.

LumoCad

The platform

The 3D editor and its building data. It is the only place real buildings change, and its own undo/redo is the safety net.

Runs: production for customers.
Ships: hotfixes must stay possible.

How your work will look, step by step

You work downstream, close to the finished plan: windows, doors, wall types. Piotr works upstream: backup, golden set, wall boundary. Arne called it "working backwards": start from the end state and find the bottlenecks.

  1. Pick one gap after review with Piotr

    The ten-gap list is paused. Several items (scoring, outline filter) overlap with Piotr's golden set, and two agents on the same thing would collide. Review the list together first, then claim only the downstream items.

  2. Open a Workbench chat in the platform repo works today

    Start it from the ticket in Work Hub so the chat carries the ticket. The agent reads the repo's AGENTS.md for the Marvin rules and the setup steps.

  3. Let the agent build and try the change

    after Piotr's merge With Calvin the agent builds a tool, runs it on a live building, looks at the building state and decides to iterate or undo, all in one loop. today Without Calvin you run the local app and unit tests, and you or the agent look at the result by hand.

  4. Measure it against the golden set after Monday 9 Nov, Piotr

    No measure exists yet that says "this wall layout is good". Until it does, a result is a picture someone likes, not proof.

  5. Commit small and standalone works today

    One idea per commit so the other two can cherry-pick it. Push to the shared branch Piotr creates, not to development or main.

  6. Marvin picks it up

    A new capability becomes a Marvin tool or read, behind the experimental flag. The architect sees a proposal, presses Approve, and Undo still works.

Why Workbench stays separate from Calvin. They solve different problems and do not overlap. Workbench is where you and the agent talk, hold tickets and review diffs. Calvin is what the agent uses to touch LumoCad's live state. You can use Workbench without Calvin (you do today); you cannot meaningfully use Calvin without some chat window on top of it.

What we learned in the meeting

From the transcript of 6 November 2026 (you, Piotr, Arne). These are things people said, not things I checked in the code, except where marked.

1. The names are now settled
  • Calvin is a connector, not an LLM and not a full harness. It gives a coding agent live access to LumoCad's building tree. The harness is Codex plus Calvin.
  • Marvin is the architect-facing chat. It has to stay stable and must not run code.
  • Calvin is a development tool only: never in production, never used to correct real buildings.
2. Calvin demo: what it showed and what it did not prove
  • It works on the pure building tree (storeys, rooms, measurements) inside the live session, not through the API or database. Arne called this much cleaner for agents, because the database holds many differently linked objects that must be crawled.
  • In about a minute it wrote a floor-sorting algorithm for 10 to 12 rooms. It invented a "room core" (the area cleanly covered by measurements) and used panorama tags to guess where doors are.
  • Arne was candid that it may be overfitted to the one building used. That is exactly why a golden set is needed before judging quality.
  • It can build a tool, use it in the same session, look at the result and undo. All writes are logged, and a hard block stops it from touching buildings it was not authorised for.
  • Limit: it is not headless. If LumoCad reloads (when the XState tree structure changes), someone must keep the tab visible. Overnight unattended runs would need more work.
3. Marvin's known weakness: no real memory between messages
  • Marvin was designed as a one-shot agent: prompt and tools in, data out, done. There is no native session continuity.
  • The MongoDB you set up is a workaround that simulates continuity across messages. Burak (who reviewed the setup with Arne) said he would have designed it differently. Acknowledged, not resolved.
4. Branches and deployment
  • Everything is local today. Marvin has never been deployed; Calvin lives only on the local Vite server.
  • Keep this work off development and main for now, so a hotfix for a real project never has to untangle agent work.
  • A third shared branch (tentatively "agent-stage") becomes the day-to-day target for all three of you. Piotr creates it after merging his harness.
  • Marvin moves to development/main fairly soon behind an experimental flag. Without a database and API keys, the chat tab shows a graceful "not set up" message and breaks nothing.
  • Calvin can go to main immediately: it has no production surface.
  • Your only real code change to Marvin was routing its writes through LumoCad's undo/redo instead of straight to the API. The rest of your Marvin work is instructions in the agent file.
5. The wall-creation fix: still open
  • Wall creation failed with "cannot create an outer wall loop" after a slab update. Arne and Piotr each have a fix.
  • The transcript says the team leaned to Arne's. Your recollection is that Piotr showed his working at the end and the room preferred it. Treat it as undecided. The final answer is whatever Piotr merges.
  • Arne's fix was written entirely by a coding agent and not reviewed by hand; Piotr wants to run both on buildings he knows well.
  • Consequence for us When we merged development we kept Arne's join and step logic in boundaryExternalWallJoinGeometry.ts and boundaryExternalWallLoop.ts. If Piotr's wins, those files may have to give way.
6. The golden set: the ruler everything else waits for
  • A hand-curated set of buildings with known-good results, at least two, and some must be made by hand because few clean examples exist.
  • Method: build measures on the golden set, check them on separate test buildings, then use set plus measures as the objective benchmark for all agent work.
  • It replaces today's manual judging (Kim reviewing five rooms at a time: "fix room five but keep the solution for one to four").
  • Piotr finishes and fully tests the backup system on Friday 6 Nov and starts golden-set cases on Monday 9 Nov.

Ground rules between the layers

These came up in the meeting or already exist in the Marvin instructions. They are what keeps the loop safe.

WHAT NEVER CROSSES

  • Marvin never runs code. Changing LumoCad or its tools is the team plus a coding agent.
  • Calvin never reaches production and never edits real customer buildings.
  • Approve is a human button on a card, not a tool the model can call.
  • Agent work stays off development and main until we say otherwise.

WHAT KEEPS IT SAFE

  • Every Marvin change goes through LumoCad's editor, in one undo batch.
  • Calvin writes are logged and limited to authorised buildings.
  • Small standalone commits so each of you can cherry-pick the others' work.
  • A hotfix path to main that carries no Marvin code (your separate hotfix checkout).
