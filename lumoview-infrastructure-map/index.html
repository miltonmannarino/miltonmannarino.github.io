Lumoview · infrastructure explainer

Lumoview infrastructure, from scratch

Everything that keeps the Lumoview app running: what each piece is, where it is written down, how to look at it, and how to change it. No prior knowledge assumed.

As of 20 November 2026. Read from the Lumoflow repo (origin/development 597cfa1, which has the same resources as main) and the api repo (development cba640a). Section 10 lists what was not checked.

1The short version

  1. Almost everything runs on Scaleway, a French cloud provider, in its Paris region. Development and production are two separate Scaleway projects, each a full copy of the other.
  2. One repository, Lumoflow, describes the infrastructure as text files. A tool called OpenTofu reads them and creates or changes the real resources. Pushing Lumoflow to development changes dev. Merging to main changes prod after someone approves it in GitHub.
  3. Each app repository deploys its own code into the slots Lumoflow created. That covers api, platform, lumowave, lumoplan, marvin and the workflow repositories.
  4. The API is two processes built from one codebase. The web server answers browsers and runs as a serverless container. The worker runs long tasks from a queue on its own virtual machine. The worker reaches browsers through a small relay server called Valkey.
  5. Data lives in two places. The database is MongoDB Atlas, a hosted MongoDB service outside Scaleway. Files live in Scaleway Object Storage buckets. Logins go through Auth0.

2The ideas you need first

Each term below shows up later on this page. Read them once and the rest makes sense.

Cloud provider, project, region
A cloud provider rents out computers, storage and networking. Scaleway groups resources into projects, and Lumoview has one project per environment. A region is a data-centre location. Ours is fr-par (Paris), and machines sit in zone fr-par-1.
Environment
A complete, separate copy of the system. Development (dev) is for testing and production (prod) is what customers use. Names end in the environment, as in api-development and api-production. Dev hostnames end in lumodev.cloud and prod hostnames end in lumoview.com.
Docker image, registry
An image is a packaged app: code, Node.js and libraries, frozen into one file that runs the same everywhere. A registry stores images. Ours are Scaleway registries named app-container-<env> for the apps and job-container-<env> for workflows. Example: api:cba640a49183 is the API image of that commit.
Serverless Container
Scaleway runs your image only when requests arrive and adds copies under load. With a minimum of zero it shuts down when idle, which saves money. The cost is a cold start: the first request waits while it boots. Size is given in mCPU, thousandths of a CPU core, so 560 mCPU is about half a core.
Instance (virtual machine)
A rented computer that stays on all the time. We use two kinds: the API worker and the Valkey server. Type DEV1-S has 2 virtual CPUs and 2 GB of memory. STARDUST1-S has 1 virtual CPU and 1 GB.
Serverless Function, Job
A function is a small piece of code that wakes up for one event, for example a queue message, and must finish quickly. A job is a container that runs a longer batch to completion and then stops.
Queue (SQS)
A mailbox for work. One side posts a message such as "copy building X". A consumer takes it, does the work, then deletes it. While the work runs, the message is hidden from other consumers. That hidden period is the visibility timeout. If the consumer does not delete the message in time, the message reappears and runs again. This is how one building copy ran about 130 times in dev on 19 November.
Object Storage, bucket
A file store reached over the web, compatible with Amazon S3. A bucket is one named store. Files are addressed by a key that looks like a path. Example: building/<id>/file/scan.json in bucket files-production.
Secret Manager
Scaleway's safe for passwords and settings. Each secret has numbered versions, and adding a version is how you change it. Our apps read their secrets only when they start, so a change needs a restart.
Valkey
A fast in-memory server, the open-source continuation of Redis. We use it as a relay. The worker publishes "copy 40% done" to Valkey, and every API instance listening there forwards it to the right browser over Socket.IO, a live connection between browser and API.
Infrastructure as code, OpenTofu, state
Instead of clicking in the Scaleway console, resources are described in .tf files. OpenTofu, the open-source fork of Terraform, compares those files with reality and makes the changes. It records what it created in a state file, kept in bucket lumoflow-tofu-<env>. Anything clicked by hand is invisible to it.
CI/CD, GitHub Actions
Continuous integration and deployment: scripts that run on every push to test, build and deploy. Ours are GitHub Actions workflows, YAML files in each repo's .github/workflows/. Note that "workflow" also names our queue-driven processing services, which is a different thing.
Health probes
Scaleway keeps calling an address such as /healthz to check the app is alive. A liveness probe restarts or rejects an app that stops answering. A startup probe gives a slow-starting app extra time before liveness checks begin.
Logs, Cockpit, Grafana, Promtail
Cockpit is Scaleway's log and metrics store, and Grafana is the screen you search it with. Serverless resources send logs there automatically. Virtual machines need a forwarder, and ours is Promtail.
DNS, Cloudflare
DNS turns a name like api.lumoview.com into an address. Our DNS lives at Cloudflare. For the Platform site, Cloudflare also adds HTTPS and redirects plain HTTP.

3The map

One environment. Production and development each have this whole picture. The orange boxes are the parts you deal with most.

  1. The browser looks up our names at Cloudflare.
  2. It loads the Platform app, plain files served from a bucket.
  3. The Platform app calls the API for data.
  4. The API posts long work as a message on a queue.
  5. The worker takes the message and does the work.
  6. The worker publishes progress to Valkey.
  7. Every API instance hears it and forwards it to the right browser.
  8. Other queues wake the Lumoflow workflows.
  9. A push to GitHub runs Actions, which build images and deploy every box in Scaleway.

API web server

The program the Platform app talks to. It is an Express server written in TypeScript, bundled into one file and run by PM2, a process manager that restarts Node if it crashes. It answers on port 5500, and Scaleway checks /healthz.

Defined in
Lumoflow infra/opentofu/scaleway/main.tf, resource scaleway_container.api. That file sets size, scaling, probe, hostnames and the non-secret environment variables.
Deployed by
api repo, .github/workflows/deploy.yml, on every push to development or main. OpenTofu ignores the image field, so the API's CI owns which code runs and Lumoflow owns everything else.
Look at it
Scaleway console, Serverless, Containers, container api-<env>. Lumowave /infrastructure. Logs in Lumowave /logs with origin api.
Change it
Code: push to api. Size, scaling or probes: edit Lumoflow. Settings: new version of secret container-secrets, then redeploy.
Watch out
Start-up takes up to about 60 seconds on half a CPU core, and the liveness probe gives exactly 60 seconds (12 checks × 5 s). One dev deploy failed on this on 20 November. It has no startup probe yet.

API worker

The same API image started with ROLES=worker, so it runs no web server. It reads tasks from the API's task queue and runs them: building copies, Notion sync, notifications, Airteam import and the hourly temp clean-up. Tasks get a 15-minute hold on their message and are cut off after 10 minutes.

Defined in
Lumoflow main.tf, resource scaleway_instance_server.api_worker, plus api-worker-cloud-init.yaml.tftpl. That template installs Docker, writes the settings file, and adds a small supervisor script that pulls api:worker and keeps it running. It also starts Promtail to forward logs.
Deployed by
api repo, workflow "Deploy API worker", started by hand with a choice of environment. It reboots the VM, and on boot the supervisor pulls the newest api:worker. Run it only after the API deploy has finished, because that deploy builds the image.
Look at it
Scaleway console, Compute, Instances. Lumowave /logs with origin worker. Grafana in Cockpit, custom logs source lumoflow-<env>, label job="lumoflow-api-worker".
Watch out
Prod worker logs were not arriving in Cockpit on 20 November. Node crash messages, such as running out of memory, never reach Lumo logs. The timers inside the worker restart from zero on every reboot.

Valkey

The relay that lets the worker reach browsers. The API and the worker both connect at start-up. Without it the worker logs Socket.IO publisher not started and toasts such as "Duplication completed" never appear.

Defined in
Lumoflow main.tf, resource scaleway_instance_server.valkey, plus valkey-cloud-init.yaml.tftpl. OpenTofu generates the password and writes the connection settings into secret api-valkey.
Look at it
Compute, Instances, valkey-<env>. Its logs go to the same Cockpit custom source as the worker's.
Watch out
Port 6379 is open to the whole internet and protected only by the password.

Queues and workflows

Two families of queues exist. The API's own task queue feeds the worker. It was created by hand and its address lives in container-secrets as SCALEWAY_SQS_TASKS_URL. The Lumoflow queues, one per workflow, are named lumoflow-<workflow>. When a message lands there, Scaleway wakes the matching function or container directly.

Lumoflow itself

The repository Lumoview-Building-Analytics-GmbH/lumoflow. The parts you will touch:

main.tf
Every resource on this page, about 1,700 lines.
variables.tf
Inputs and defaults. Example: cockpit_logs_retention_days = 7.
*.tftpl
Boot scripts for the worker and Valkey VMs. They run only when a VM is created. To re-run one, raise its generation number variable, which rebuilds the VM.
CI
.github/workflows/infrastructure.yml checks formatting and validity, then runs tofu apply -auto-approve. Production waits for approval in the GitHub production environment.
Docs
docs/operations/ (infrastructure, deployment, secrets) and infra/opentofu/scaleway/README.md.

5How a change goes live

You change…You doWhat happens
API codePush to development, or merge to main"Test and deploy API" runs the tests, builds the image, pushes api:<commit> and api:worker, and points the container at the new image. Scaleway starts it and waits for /healthz.
Worker codeSame push, then run "Deploy API worker" for that environmentThe VM reboots and pulls api:worker. Nothing happens to the worker until you do this second step.
PlatformPush the platform repoIt builds the site and copies the files into the bucket with aws s3 sync.
InfrastructurePush LumoflowValidates, then applies to dev right away. Prod applies after approval.
A workflowPush its repoIts own CI deploys. Dev is automatic and prod needs approval.
A setting or secretNew version in Secret ManagerNothing until restart. Then redeploy the API and run "Deploy API worker".

Rule of thumb: Lumoflow decides how big and how wired a thing is. The app repo decides which code runs in it. Secret Manager decides which settings it starts with.

6Secrets and settings

Settings come from three places, read in this order at start-up. The non-secret environment variables come from Lumoflow. Then the bootstrap code in the API (bootstrap.ts) fetches container-secrets and finally api-valkey. A later value wins. The bootstrap gives up after 4 seconds and starts anyway.

8One click, end to end: Duplicate building

Following one real action ties the pieces together.

  1. You click Duplicate in the Platform app, which your browser loaded from the Platform bucket.
  2. The browser calls the API container. The API checks your Auth0 login and posts a "copy building" message on its task queue.
  3. The worker VM takes the message. It writes a job record in MongoDB Atlas so only one attempt owns this copy.
  4. It copies every file of the building inside Object Storage, under building/<new id>/, then writes the database rows.
  5. Along the way it publishes progress to Valkey. The API instance holding your browser's Socket.IO connection forwards it, and you see the toast move.
  6. In production only, it creates a page for the new building in Notion.
  7. It deletes the queue message. If it needs more than 10 minutes, the queue hands the message out again. The job record now stops that second attempt.
  8. Every step logs to Lumo logs, which you can search in Lumowave /logs under origin worker, task copyBuilding.

9Proposed improvements

Ordered by how much trouble each one prevents for the effort. None of these has been started. Each needs a go before anyone builds it.

HighGive the API container a startup probe

Deploys fail at random when boot takes longer than 60 seconds. Copy the startup probe the workflow containers already have: 30 checks × 5 s, so 150 seconds to boot before liveness checks start.

Where: Lumoflow main.tf, scaleway_container.api. Size: a few lines.

HighBring the API task queue into Lumoflow and line up its timers

The queue the worker reads was made by hand, so nobody can see its visibility timeout in git. The worker asks for a 15-minute hold and cuts tasks off at 10 minutes. Scaleway refused the worker's request to extend that hold in dev. Mismatched timers are how one copy ran about 130 times. Manage the queue in Lumoflow with a timeout longer than any task can run, and give long tasks their own limit.

Where: Lumoflow main.tf, plus the API's services/tasks/consumers.ts. Size: medium. Bringing an existing queue under OpenTofu needs an import step.

HighAlerts, and worker logs that always arrive

Fix Promtail forwarding on the prod worker. Then add Cockpit alerts for these cases: a worker restarting repeatedly or running out of memory, queue messages stuck in flight, the API health check failing, and a deploy failing. Send them to email or Slack.

Where: Lumoflow (Cockpit alert rules, worker template), Lumowave for display. Size: medium.

HighDeploy the worker in the same run as the API

Today the worker needs a second, manual run, and if it starts too early it reboots onto the old image. Add a job after "Deploy API" that restarts the worker. Tag the worker image with the commit too, so you can see which code the worker runs and go back to an older one.

Where: api .github/workflows/deploy.yml, Lumoflow worker template. Size: small to medium.

MediumStop dev from writing into production storage

File rows in the dev database name the production buckets. So a Duplicate in dev writes new files into production storage, and clean-up there is risky. Point dev rows at a dev bucket, or copy the needed files once.

Where: one-off data migration plus a guard in the API. Size: medium.

MediumClose Valkey to the internet

Its port is open to every address and protected only by a password. Put Valkey, the worker and the containers on a Scaleway Private Network, or at least allow only known addresses.

Where: Lumoflow security group and network. Size: medium. First check which Private Network options Serverless Containers support.

MediumOne key per service

One shared Scaleway runtime key is used by the API, the worker, Lumowave, Lumoplan and the workflows. If it leaks, everything is exposed, and rotating it touches everything. Lumoflow already supports creating dedicated keys (create_runtime_iam_identity). Extend that to one key per service, each with only the access it needs.

Where: Lumoflow IAM resources. Size: medium.

MediumWrite down what belongs in container-secrets

Its contents are edited by hand and invisible in git. A missing key shows up only as odd behaviour, like the empty Notion token. Keep a list of the expected key names in the api repo. At start-up, log the names that are missing, never the values.

Where: api config.ts or bootstrap.ts, plus .env.dist. Size: small.

MediumMove the worker's timers to real schedules

The hourly clean-up, the two-hourly notifications and the Airteam import are timers inside the worker. Every reboot restarts them from zero, and a second worker would run them twice. Scaleway cron triggers, like the one hours-reminder uses, would post the task on a fixed schedule instead.

Where: api worker.ts, Lumoflow. Size: small to medium.

LowSmaller clean-ups

Delete the old Kubernetes files in the api repo (k8s/), which no workflow uses. Keep prod worker logs longer than 7 days. Show worker VM logs in Lumowave /infrastructure. Confirm Sentry is reporting, and decide whether its start-up instrumentation is worth about 40% of API boot time.

10How sure this page is

  • Read from code: Every name, size, timeout, hostname and deploy step above comes from Lumoflow main.tf, variables.tf, the CI files and the api repo as of 20 November 2026.
  • Seen in practice on 20 November: Worker progress reached browsers through Valkey in dev. The dev deploy failed once on the 60-second limit. Prod worker logs were missing in Cockpit.
  • Not checked: The live Scaleway state, which can differ from the files if someone clicked in the console. The contents of container-secrets.
