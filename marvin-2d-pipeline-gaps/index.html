Ten places to improve: from point cloud to 2D plan

The goal is to turn a scanned building into a finished 2D floor plan with as little hand work as possible: model the sorted point clouds, generate the geometry, draw the plan. The calculations for every step already exist in LumoCad, and Marvin (the chat inside LumoCad) can call all of them. What is missing is proof and glue: nobody has measured how good the result is on a real floor, and several steps are wired together badly or not at all. Below are the ten places where work pays off most, ranked.

What the evidence says today

  • The only live test on a real building is a 1.25 mm room move (Gewobag OG04, 9 Oct).
  • The one room outline the AI drew from the cloud (room "Flur 32") was rejected by the user.
  • Arne's own benchmark on two real floors: 0 safe room placements, 38 and 41 rooms unresolved, 0 walls, and "manual correction counts remain unmeasured".
  • The automatic "finish floor" mode is switched off.

Start with

#1 Measure first. A scorecard on the golden building, before any other change.

In parallel, the cheap ones: #2 (one day), #6, #8, #9.

How this was checked

Four read-only code reads on 5 Nov plus hand checks. verified means read and confirmed by hand today; from the read means reported by a code read. No tool was run on a building.

The answer in one paragraph

There is a deterministic tool that fits a room outline to the point cloud, a tool that draws the floor slab around the rooms, a tool that generates walls from the gaps between rooms, a tool that places measured doors and windows into walls, a plan writer with 52 kinds of warnings, and a six-stage "is this floor ready" check. Marvin has 84 tools to call all of that. But Marvin's own outline fitter is wired to an older algorithm than the button a person clicks; walls are drawn from room outlines alone and never look at the cloud; nothing creates a door or window from evidence; generated walls have no type; "ready" means the geometry agrees with itself, not with the scan; the instructions Marvin gets are 81,000 characters per message and contradict each other; and there is no way to run any of it outside a person's browser. None of this is measured. So the first move is a scorecard, and the next moves are the cheap fixes while the scorecard is built.

The ten places, one by one

Each has the same shape: what happens today, why it matters, what to change, and the first step.

1 A scorecard on a golden floor before any other change

measurement 1 week · Milton, Piotr

Today

Nothing scores what Marvin produces. The service has 13 live test scenarios, but they check that the right tools were called in the right order on hand-written fixtures, not whether the geometry is right. The one benchmark that uses real scan data measures the room-placement search, and it came out negative (0 safe placements on two floors). There is no number for "how far is the outline from the cloud", "how many of the generated walls match what the architect finally accepted", "how far off is each door", or "how many fixes did the person make afterwards".

Why it matters

Arne's lesson from the last attempt: take one failing case and fix it; an automatic loop over 50 prompt variants did not work. That needs a case and a number. Without them every item below is a guess, and nobody can tell whether a change helped.

Change

Four numbers, printed by a script after a Marvin pass on a copy of the golden building (Hohental, arriving from Piotr the week of 9 Nov) and on the frozen Gewobag floor OG04:

  • For every room outline edge, how much of the cloud supports it. The rule exists already in the code (points within 30 mm of the edge, at least 70 % coverage).
  • How many generated walls match the human-accepted walls. Every hand-in uploads the approved layout, so the "correct answer" is already there for free.
  • Door and window position error against the accepted placements.
  • How many edits the person made after the pass.

First step

A headless browser run (the Playwright setup already used for demo videos) that opens the copy, triggers one tool, and writes the four numbers to a file. Item 10 replaces the browser later.

2 Marvin's outline fitter is a weaker copy of the human's button

better tool verified 1 day · Milton

Today

The button a person clicks, "Estimate room boundaries from edge detection (v2)", runs the newer fitting algorithm and hands it the building's reference directions (helper lines a person draws along slanted walls) and the drawing grid. Marvin's tool for the same job, plan_room_outline_fit, defaults to the older v1 algorithm, which can fall back to a plain convex hull, and passes neither the reference directions nor the grid. So Marvin gets worse outlines than the person for no reason. Two more limits: the tool refuses rooms that already have an outline, and if a scan lacks its edge analysis the room silently fails, with no way for Marvin to request the analysis.

Where: features/assistant/editorOps/service.ts:474 (default method), editorOps/outlineFit.ts:46-49 (no reference directions), versus TopViewToolbarCad.tsx:913 and hooks/useStoreyRotLidarBoundaryFitRuntime.ts:128-193.

Change

Default to v2, pass the reference directions and the grid, allow replacing an outline when the measured acceptance check that already exists passes, and add a read tool that says which scans lack analysis. Then the October audit's item T1-6: propose the helper lines for slanted walls automatically (a function that clusters wall directions already exists), because without them slanted walls drop out of the outline silently.

3 Two competing outline methods and no acceptance rule

Marvin setup better tool 3 days · Milton, Arne

Today

Marvin has two ways to get a room outline from the cloud. One is the deterministic fitter above, allowed only for rooms with no outline. The other is surprising: the browser renders the cloud as a 1200 × 1000 pixel image with the panoramas, and the AI model itself draws the polygon by looking at the picture. That path needs an existing outline (checked only after the expensive image capture and the model call), allows one retry, caps its own confidence at "medium", and its one real result was rejected. In the automatic "finish floor" mode the drawing tools are switched off, yet the readiness check still tells Marvin to use them for a room without an outline. No instruction anywhere says what a good enough outline is; the words are "supported", "safe" and "plateau", without numbers.

Where: outlineReconstruction/service.ts:95 verified, lumoagent/internal/marvin/floor_request_tools.go:46-54 verified, floorReadiness/service.ts:~97 from the read.

Change

One policy, written in the instructions and enforced by the tool: fitter first; model drawing only when the fitter fails, and accepted only when the same numeric check passes (edge support, no scanner position more than 300 mm outside the polygon, area close to the fitter's best attempt). Either make the drawing tool work for rooms without an outline, or stop offering it for that case. Make the readiness text say only what is allowed.

4 Walls come from outlines only; exterior thickness is a default

better tool verified 1–2 weeks · Milton

Today

The wall generator never reads the point cloud. It takes the gaps between room outlines as interior walls, and the band between the rooms and the slab outline as exterior walls. The slab outline is made by pushing every room outline outwards by a fixed 40 cm, so every exterior wall is 40 cm thick by default, not because anyone measured it. Any check against the cloud happens only afterwards, as an audit. Marvin adds two refusals the button does not have: it will not generate walls on a floor that already has walls, and it will not handle a slab with holes (a light well, a stairwell) although the button does. Regenerating with the button deletes all walls on the floor and detaches every door and window.

The architects' Revit workflow reads the exterior thickness from a visible opening or from the drone model and ends with "does the model sit on the cloud". Today neither happens.

Where: constants/slabBoundaryFromSpaces.ts:1, utils/geometry/boundaryWallPreview.ts and the boundaryExternalWall*, boundaryInternalWall* files, features/assistant/creation/planning.ts:39,45.

Change

  • Measure exterior thickness per façade: from the cloud at door reveals and window jambs, or from the drone model where it is aligned (audit item T2-13). Feed that into the slab offset per façade instead of one global 40 cm.
  • Let Marvin's planner handle slab holes like the button does.
  • A regenerate mode that keeps walls with attached doors and windows and replaces only the rest.
  • Move the wall-refinement tool off its direct server writes onto the editor's own wall machine (this is step 4 of the existing tool-map plan).

5 Nothing creates a door or window from evidence

missing piece verified 2 weeks · Milton, Piotr

Today

No code in LumoCad or Marvin creates an opening from the cloud or from the photos. Marvin can only place doors and windows that already exist as records, and to do that it needs a person's click in a panorama, or scan points tagged "door" as a hint, or the model reading the door's edges off a calibrated image. The swing direction comes only from a saved placement axis; otherwise the opening is handed back to the editor. Meanwhile three pieces exist and are not connected: the server already outlines doors and windows on every panorama with a vision model when it is uploaded; a server task can turn those outlines into draft marks but a person has to start it; and the capture app records each door's width, height and the two rooms it connects.

Where: features/assistant/openingPlacement/capture.ts:68,78, openingPlacement/evidence.ts; the server pieces are objectTags and the PROCESS_OBSERVATION task (October audit items T1-2 and T1-3).

Change

Chain the three: run the vision outlines into draft marks automatically on upload; match each mark to the hand-measured opening by the rooms they share, the width and door-versus-window; then let Marvin's placement tool position it from the gap in the wall's cloud (width and position from the floor cloud, sill height from the section cloud, the Revit method). Swing: a default from the capture's "leads to" and the smaller room, flagged for the person. Marvin's part is the last step and the review card; the first two are server batch jobs.

6 Generated walls have no type

missing piece verified 3 days · Milton

Today

A wall type ("24 cm masonry", "10 cm drywall") is what the client and Revit need. The generator never sets one. The Wall Type Organizer groups walls by thickness and suggests, but applies nothing. No Marvin tool touches types. The plan carries the type only as hidden metadata. The October audit called deciding the type "the one pure judgement step left" at the wall station.

Where: utils/geometry/boundaryWallPreview.ts and boundaryExternalWallLoop.ts (no wallTypeId), utils/floorplan/extractFloorPlanWalls.ts:86-90.

Change

A plan_wall_types tool over the thickness histogram that already exists: cluster the thicknesses, propose a type per cluster from the organisation's catalogue, apply through the wall machine in one undo batch after approval. Small and self-contained; a good single commit for the cherry-pick workflow.

7 "Ready" never looks at the cloud, and there is no single gate

better tool from the read 1 week · Milton

Today

The floor readiness check says "complete" when the saved geometry agrees with itself: the slab minus the rooms equals the walls to within 1 mm², openings are attached, loaded data matches saved data. Its own note says this is "not independent survey accuracy". The one field that would say whether the geometry agrees with the scan has never been true on a real floor. The plan's 52 warnings are a display list whose severity is a tunable map, and some gaps are silent: a missing room number, an unknown north direction, a living-area factor that silently defaults to 1. No check exists for a wall thickness that makes no sense, a room with no door, a door that sits between the wrong two rooms, or a room area that does not match the scan. The human QC checklist is a separate thing, stored in one person's browser.

Where: features/assistant/floorReadiness/service.ts:195, wallCoverage.ts:25, constants/floorplanWarnings.ts:74, utils/floorplan/extractFloorPlanRooms.ts:366,376.

Change

  • Add a per-wall "does the face sit on the cloud" check (the support rule from item 1) and the four architect checks above to readiness.
  • Define one pass/fail gate with named blockers, used both when Marvin claims a floor is complete and by the QC hand-in (audit items T1-1, T2-10, T2-14).
  • Turn the silent plan omissions into warnings.

8 81,000 characters of instructions per message, with contradictions

Marvin setup verified 3 days · Arne, Milton

Today

Every time Marvin asks the model something, it sends the complete instruction text first. Measured today: 81,331 characters, about 20,000 tokens, on every single call. In the automatic floor mode 22 tools are switched off, but the text still describes them; the only correction is one sentence. The rules contradict each other: "missing evidence is not permission to guess" sits next to "always try a closed best-effort polygon, hidden areas are normal, not a reason to refuse"; "clarify when the target is unclear" sits next to "do not ask whether to investigate, calculate, or continue". No instruction gives a number for what an acceptable outline, wall or opening is. Some tool descriptions have numbers glued to words ("hard500", "default100"), and one tool advertises four operations where the automatic mode accepts one.

Where: lumoagent/internal/marvin/roadmap_tools.go:19 (assembly), floor_tools.go:65, single_pass_draw_prompt.txt:27-29, level_improvement_prompt.go:3, floor_request_tools.go:46-54. Marvin's instructions are Go code, so a change means a rebuild and restart.

Change

Build the instruction text per mode from the tools actually offered. One short procedure: readiness, outlines, slab, walls, openings, verify. Put in the numeric checks from items 1, 3 and 7. Delete the contradictions and fix the glued numbers. Measure item 1 before and after.

9 Marvin starts blind and gets no feedback after a save

Marvin setup verified 3 days · Arne, Milton

Today

At the start of each message Marvin receives a short summary: building name, active level, how many rooms and walls, how many plan warnings. Nothing about the scans: how many, which rooms have a cloud, which scans are still of type "Unknown" (the thing that blocks a hand-in), whether the edge analysis exists. Marvin has to spend tool calls and model calls to find out, and gets 24 model calls per turn. After a person approves and the save finishes, the model receives only a status and an id, no before-and-after, nothing to learn from. When a person rejects a proposal there is no way to say why, and in the automatic mode a rejection pauses the whole floor. Marvin has no tool to see the sorting state of a scan, and none to change it (sorting stays human, but seeing it is needed).

Where: features/assistant/browserTools.ts:208-224 (the summary), lumoagent/internal/marvin/runner.go:702-727 (what comes back after a decision).

Change

Add a scan inventory to the start summary (per room: scans, analysis present, Unknown count). Return the before-and-after numbers from item 1 with every save result. On "Reject", ask for one line and pass it to the model. Add a read tool for scan types so Marvin can refuse early with the right message.

10 No way to load a building outside the browser

missing piece enabler · 2 weeks · Piotr, Milton

Today

Every calculation above runs only inside a browser tab that a person has open. There is no nightly scoring, no "fit all missing outlines as soon as the scans arrive", and item 1 has to go through a browser automation with a copied login. The October audit listed this as prerequisite P1; Arne named the same gap on 4 Nov: no local LumoCad access to check against a golden dataset while coding.

Change

A headless loader: fetch a building's objects and clouds through the existing API with an organisation API key, build the editor's state machines without React or the 3D canvas (they are plain XState), and expose the pure functions (plan preparation, the fitter, the wall generator). For the next weeks the browser automation is the stand-in.

What to park

  • The room placement and registration stack. At 4,266 lines it is Marvin's largest module, and it targets the room puzzle, which the 4 Nov decision leaves with the preprocessing team. Its only real-floor result is negative. Keep the evaluation tool as a check; stop investing in the search until a puzzled Hohental shows where rooms still move.
  • Model-drawn outlines as the main method (item 3): fallback only.
  • Dimension lines, sheets, title block, room-numbering convention, sections, roofs and stairs: human by decision (Rio, 2 Sept; the roof and stair pause of 4 Nov). Marvin may check them, not author them.

What was not checked

  • No tool was run on a building today. The thresholds quoted are constants in the code, not measured behaviour.
  • The quality of the server's vision outlines and of the draft-mark task was not inspected.
  • Items 4 and 5 assume the capture app's door measurements are reliable; the October audit notes cases where the unit is ambiguous.
  • Windows (Arne's machine) is untested throughout.

Glossary

Point cloud
Millions of measured dots from the laser scanner, each a spot on a wall, floor or object. Raw dots, not a drawing.
Sorted
Each scan assigned to its room and given a type (room scan, section, stairs, door, discarded). A scan of type "Unknown" is unsorted and blocks the hand-in.
Room outline
The clean polygon along the inside face of a room's walls. Area and walls are derived from it.
Slab
The floor plate of a level; its outline bounds the exterior walls.
Reference directions
Helper lines a person draws along slanted walls so the fitter does not assume every wall is at a right angle.
Readiness
Marvin's six-stage check of a floor: inventory, rooms, slab, walls, openings, verification.
Instructions (prompt)
The text sent to the AI model before every request, telling it what Marvin is and how to behave. In Marvin it is Go code.
Token
The unit the model reads and bills by; roughly four characters.
Golden building
A finished, human-approved building kept as the "correct answer" to measure tools against. Hohental is the first.
Headless
Running a calculation on a server without a browser window.
