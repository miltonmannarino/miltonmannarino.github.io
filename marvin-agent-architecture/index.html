Marvin: an AI architect that works inside LumoCad

Marvin is an agent that does an architect's routine modelling steps inside the LumoCad editor and shows every change as a preview that a person approves. It runs on one Mac today except for the model call. The first step of making it use LumoCad's own functions is built and tested. Four things need a decision or a hand-off, not more code: the model key, the real-app run, Arne's design document, and a few open decisions.

The goal

Make the architect a reviewer, not an executor. A scanned building goes in; a correct 2D floor plan with its areas comes out; people only check.

The direction the team set on 4 Nov 2026. The north star is a highly automated 2D workflow. Active work on roof details and on 3D stair geometry is paused. Stairs only need their area contribution and a drawing. IFC export and the HotCut format are dropped for now. Automation should go where the work is expensive, the architect layer: naming rooms, fixing outlines, building walls, placing doors and windows. Sorting scans stays with the cheaper sorting layer for now.

Two agents, one shared toolbox. Marvin is the live agent inside LumoCad. It uses LumoCad's tools on a real building, cannot read or change the code, and cannot approve its own changes. A second, local coding agent is a normal coding assistant with the code and test buildings. It runs a tool on a test building, sees the error, fixes the tool, and runs it again. Marvin gets better because the tools get better.

How we will know it works. The first test building is a new-build with flat roofs that already has boundaries, sorting, walls and windows done. The plan is three working copies on the dev server, one each for Arne, Milton and Piotr, plus one untouched original to clone again. Each person reverts a copy to the state just after sorting and models it, then the outputs are compared: where people got stuck, how accurate the result is, how consistent. Piotr is targeting the start of the week of 9 Nov for the reset system.

What it replaces. A person today clicks through each station of the pipeline by hand. The earlier audit of that pipeline (the Agent Workforce page) ranked which steps an agent could take over. Its suggested first pilots included readiness reports and door and window placement, and Marvin's tools already touch both.

The architecture

Three parts talk to each other: the browser with LumoCad, a small Go service that runs the conversation, and a language model. Everything that touches a building happens in the browser.

  1. You type a request. The controller sends it to the service over HTTP and listens to a stream of events back (server-sent events: a one-way stream from server to browser).
  2. The service calls the language model with the conversation and the tool list.
  3. The model asks for a tool. The service forwards the request to the browser, because only the browser has the building loaded.
  4. The browser runs the tool against LumoCad: read, or compute a preview. Nothing changes yet.
  5. The result goes back to the service. Steps 2 to 5 repeat, up to 24 times per request.
  6. A change appears as a preview card on the canvas. A person presses Approve. The model cannot approve, and Approve is not a tool.
  7. On approval the change is applied and saved to the platform API.
  8. A read-back check compares the saved fields with the proposal. It never writes.

So the agent is not mostly duplication. The duplication sits in two places: the apply and save stack after approval, and about a dozen small read helpers that re-read data LumoCad already exposes.

The two rules from Arne, and what they mean in the code

  1. Stronger separation between the agent and LumoCad. Today the dependency points the wrong way: 21 core files import from the assistant folder, including every element machine, the building machine and the undo machine, and seven assistant-only event types live inside core machines.
  2. Use LumoCad's existing functions; do not double them as tools. The logic stays in the frontend. The planners mostly comply. The apply step does not: it sets positions through a private event, posts its own patches to the server and keeps its own undo history.

The two rules are one change. If an approved proposal sends the editor's ordinary events, the private events and most of the cross-imports have no reason to exist.

Step 1: approving a room move now uses the editor's own events

The first tool converted is propose_room_move. It is a small change on a local branch off Arne's: one new module, two test files and three small edits, about 430 lines in all. Nothing is committed or pushed.

Before: the assistant's private path

  1. Write a journal entry to the browser's storage
  2. Record the operation on the server
  3. Lock the room against normal edits
  4. Send an assistant-only event that sets positions directly
  5. Post patches to the platform API itself
  6. Check the saved fields
  7. Add an assistant-owned undo entry

After: what a mouse drag does

  1. Open one editor undo batch
  2. Move the room anchor; the editor moves measurements, outline, shapes and comments
  3. Read the anchor back; stop if it did not move
  4. Finalize the room, then let the editor save outline, shapes and measurements
  5. Close the batch: one Ctrl+Z restores everything
  6. Wait for the saves, then read the server fields back, without writing

Building it against the real machines exposed four traps that a mocked version would have hidden. Each is covered by a test.

  • The room anchor silently ignores a move outside Point Cloud, CAD and TGA-shapes modes, and for rooms whose annotation is complete. A naive version would have saved unchanged positions and reported success. The new code checks the result before saving and refuses with a clear message. The real machine confirmed the refusal in View, Observation and QC 3D modes.
  • With "Freeze boundaries and TGA shapes" on in Point Cloud mode, the editor deliberately leaves outlines in place while scans move. The proposal card promises the outline moves, so the new code refuses up front and names the button.
  • The editor records undo at the moment of saving, so wrapping the events in one batch gives exactly one undo step. Without it, outline and measurements would be two steps.
  • The editor's own drag does not rewrite combined door and window placements, so a move that shifts them stays on the old path.

2How to test

Three levels. The first needs nothing but the repositories. The second needs the local stack. The third needs a model key.

A. Automated checks, no key needed

In platform, on the branch marvin/native-apply:

NODE_ENV=test npx vitest run \
  src/lumocad/features/assistant/moves/nativeRoomMove.test.ts \
  src/lumocad/features/assistant/moves/manager.native.test.ts
# expect: 2 files, 21 tests passed

NODE_ENV=test npx vitest run src/lumocad/features/assistant
# expect: 292 files passed, 2,498 tests

pnpm exec tsc -b
# expect: exit 0, no output

In lumoagent, on development_ai-chat: GOTOOLCHAIN=go1.25.0 go run ./cmd/devcheck, which runs the Go checks offline with fake providers. Expect "devcheck: passed". Go 1.27 fails to build this service, so the toolchain must be pinned.

B. The assistant pane in the real app, no key needed

  1. Start the local stack: Mongo and the Go service. Start the platform dev server with the development environment setting; a production setting makes the app crash with a JSX error.
  2. Open a dev building in LumoCad on the branch. Click Assistant in the top bar.
  3. Expect the pane header "marvin · Connected", a model picker with Claude Fable 5.1, GPT-6 Astra and GPT-6 Luna, and the list "What marvin can do". Sending is disabled until a model is chosen.

C. The room move end to end, needs a model key

  1. Choose a model, then ask: "Move the room name 100 mm to the east."
  2. Expect a preview card with the outline before and after, and Approve and Skip. Nothing has changed yet.
  3. Press Approve. Expect the card to say saved and to show "Use the editor's Undo to restore this operation". There is no Undo button on the card by design.
  4. Press Ctrl+Z once. Expect the room, its outline and its scans back where they were, in one step.
  5. Refusals to try: switch to View mode and approve a move, expecting a message that the editor did not accept it and nothing changed. In Point Cloud mode turn on Freeze boundaries and TGA shapes and approve, expecting a message naming Unfreeze boundaries and TGA shapes.

D. The real-app check without the model

What the script does, and why it has not run

A script opens the dev Example Building in headless Chrome with an isolated copy of the demo login, takes the smallest level, builds a real move proposal for one room, applies it through the new code, reads the server fields, undoes with the editor's own undo event and checks that the room is back. It has a safety restore: if the undo does not restore the room, it moves the room back itself. It writes to the shared dev server for a few seconds, so the automatic safety check refused to run it. It runs only after a person decides to allow it.

What it settles: the read-back compares the proposal's patches with the fields the editor saved. Whether those agree within the tolerance used is only visible against a real save.

Unknowns and risks

  • unknown The real cost of a chat turn and of a full floor with a model: nothing has run with one.
  • unknown How the read-back tolerance behaves on a real save, see the real-app check.
  • unknown How many tools survive the design review, and how much the duplicated scoring is worth keeping.
  • risk The editor's events were built for a mouse. Room moves are now covered for modes, completed rooms and frozen outlines; the other tools are not yet.
  • risk The browser and the service must upgrade together: a version mismatch is refused. Any tool-set change in step 8 crosses that line.
  • risk The service allows one active run per user and building, enforced in Mongo with a lease. Several architects on one building will queue.
  • risk A product used by other people cannot run on a personal subscription login; it needs an API key under the commercial terms.
