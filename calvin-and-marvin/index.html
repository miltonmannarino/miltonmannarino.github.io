Lumoview · LumoCad · how the two helpers fit together

Calvin and Marvin: two helpers, two jobs

LumoCad is about to get two kinds of AI helper. Calvin is our name for Piotr's local harness and the coding agent that works through it: it helps an engineer improve LumoCad itself, trying changes on a real building in seconds. Marvin is the chat inside LumoCad that helps a person operate a building, with a preview and an Approve button for every change. They never do each other's job. Calvin sharpens the tools; Marvin uses them.

In one sentence each

  • Calvin: "I change the program and test it on live data, and I measure whether it got better."
  • Marvin: "I use the program's tools on this building for you, and I never change anything without your approval."

The idea: a workshop and a driver

A good way to hold it in your head.

Think of LumoCad as a machine that turns scans into floor plans. Marvin is the operator sitting at the machine: he presses its existing buttons for you, tells you what he is about to do, and waits for your OK. He cannot rebuild the machine. Calvin is the mechanic in the workshop next door: he takes the machine apart, tests a better part on a real building, checks the numbers, and if the new part is better it goes back into the machine. After that, the operator simply has a better machine to drive.

That split is the same one agreed on 5 Nov: the team and a coding agent change LumoCad and its tools; Marvin sits inside LumoCad with no access to the code, and he gets better through better tools and his own setup (instructions, limits, model).

Side by side

Calvin

the harness · for the person improving LumoCad

Who talks to it: an engineer, through a coding agent (Claude Code or Codex) in the repository.

  • Sees the building you have open as data: floors, rooms, scans, selection, errors.
  • Measures: for example which scan in a room disagrees with the others (a score called G1), or how well two rooms line up (G4).
  • Runs LumoCad's own tools (room autosort, fine alignment, boundary fitting) and can write new ones.
  • Changes code and data. Edit an algorithm, and the next run uses it in about 12 milliseconds, without reloading the building.
  • Safety: writes only on dev buildings you list, one undo step per run, a checkpoint first. It never commits or pushes by itself.

Marvin

the chat in LumoCad · for the person using LumoCad

Who talks to it: an architect or modeller, in the Assistant pane of the editor.

  • Answers questions about the building, navigates, explains plan problems.
  • Prepares changes as a preview ("Original" against "New"), with exact numbers.
  • Changes building data only, and only after a person clicks Approve. The model cannot approve its own proposal.
  • After saving, he reads the server back and says "saved" or "unconfirmed". The editor's normal Undo restores it.
  • No access to code. Gets better through his tools and instructions, which live in the Go service.

How a tool travels from Calvin to Marvin

One loop, with a human at both gates. Teal is Calvin's lane, blue is Marvin's.

1

Spot a weak step

Someone sees a bad result, or the scorecard shows one: an outline that sits off the scan, a wall that does not match, a door in the wrong place.

2

Try and measure (Calvin)

On the building already open in the tab, Calvin runs the current tool, reads the score, changes the algorithm, runs again, and undoes what did not help. Each try takes seconds, because edits to algorithm files reach the next run without reloading the building.

3

Put it into LumoCad

What worked stops being a lab script. Its logic moves into a normal LumoCad function with a test, so every button and every user gets it. This is also Arne's rule: use LumoCad's own functions, do not duplicate them as tools.

4

Marvin gets the tool

Marvin's tool is a thin wrapper that calls that function: a "plan" tool that prepares a candidate and a preview, and a "propose" tool that offers it for approval. Marvin's instructions are updated to say when to use it.

5

A user approves

In the chat the user sees Original and New, clicks Approve, the editor saves it through its normal path as one undo step, and Marvin reads the server back to confirm.

6

Score it on a gold building

A "gold" building is one a human has already finished and approved, so the right answer is known. Running a tool on a copy and comparing it with that answer turns "it looks better" into a number. This step does not exist yet.

An example, in plain steps

Using a real finding from this week. It is an illustration of how the loop would run; it has not been run end to end.

The finding

To draw a room outline from the scan, the editor has a button that uses the newer fitting method (v2). Marvin's outline tool uses the older one (v1) by default, and leaves out the building's reference lines for slanted walls. So Marvin draws worse outlines than a person clicking the button.

1

Calvin measures both

On a room that looks wrong, Calvin runs the fitter with v1 and with v2 (his fit-boundaries tool already offers both), and compares how well each outline sits on the scan.

2

Calvin tunes it

If v2 with the reference lines wins on the rooms checked, the fix is small and lives in LumoCad: the function that runs the fit.

3

Marvin follows

Marvin's plan_room_outline_fit is changed to use the same function with the same settings. His instructions do not change at all: he simply asks for a better outline and gets one. The user still sees the preview and clicks Approve.

4

Both are checked on the gold building

The score before and after goes on the scorecard. If it dropped on some building, Calvin sees it and goes again.

Glossary

Harness
A control panel that lets a coding agent see and drive the LumoCad tab you have open, from the command line (pnpm harness).
Lab mode
The harness setting that applies code edits to the next run without reloading the building, so a try takes seconds.
Tool
One named action: for Calvin a file in src/lumocad/lab/tools/; for Marvin a command the chat model may request.
Plan tool / propose tool
Marvin's two-step pattern: the plan tool prepares a candidate and a preview and changes nothing; the propose tool offers it for approval.
G1 / G4
Calvin's two scores: G1 shows which scan in a room disagrees with the rest; G4 shows how well two rooms line up. Both measure how well scans overlap.
Gold building
A finished, human-approved building kept as the right answer to measure tools against. Hohental is the first planned.
Allow-list
The file where the engineer lists which dev buildings Calvin may write to. Anything else is read-only.
Undo step
One Ctrl+Z. Both helpers are built so that one run is one undo step.
Branch
A separate line of changes in git. Calvin and Marvin are on different ones for now.
