Calvin and Marvin: two helpers, two jobs

LumoCad has two kinds of AI helper. Calvin is the harness inside the dev server that lets a coding agent (Claude Code or Codex) see and drive the LumoCad tab an engineer has open: it helps the engineer improve LumoCad itself, trying changes on a real building in seconds. Marvin is the chat inside LumoCad that helps a person operate a building, with a preview and an Approve button for every change. They do not do each other's job. Calvin sharpens the tools; Marvin uses them. Since 8 November both live on one shared branch, agentic-dev, and Calvin can talk to Marvin.

In one sentence each

  • Calvin: "I change the program and test it on live data, and I measure whether it got better."
  • Marvin: "I use the program's tools on this building for you, and I never change anything without your approval."

What changed between 6 and 8 November

  • One branch. Piotr created agentic-dev: Marvin, Calvin, all recent development and the backup work. Our Marvin branch is fully inside it. Milton's checkout moved there on 8 Nov; the typecheck is clean.
  • Calvin is the name in the code now, not only ours: pnpm calvin, tools/calvin/, a dashboard, and a skill a coding agent installs (Arne, 7 Nov).
  • Marvin's service moved out of lumoagent into its own repository, marvin. Browser and service now speak protocol version 31 (was 28 on 6 Nov).
  • Calvin can see and drive Marvin: send a message, read the transcript, wait for a proposal, approve or reject it, on allow-listed dev buildings only.
  • Backups. Piotr's full building backup (reset and restore of sorting, CAD, roof, floor plans, stairs) runs on every hand-in; Marvin got a create_building_backup tool.
  • The first scorecard exists: a headless benchmark for the wall generator (pnpm wall-bench). Outlines and openings are still unscored.

The idea: a workshop and a driver

A good way to hold it in your head.

Think of LumoCad as a machine that turns scans into floor plans. Marvin is the operator sitting at the machine: he presses its existing buttons for you, tells you what he is about to do, and waits for your OK. He cannot rebuild the machine. Calvin is the mechanic in the workshop next door: he takes the machine apart, tests a better part on a real building, checks the numbers, and if the new part is better it goes back into the machine. After that, the operator simply has a better machine to drive.

That split is the same one agreed on 5 Nov: the team and a coding agent change LumoCad and its tools; Marvin sits inside LumoCad with no access to the code, and he gets better through better tools and his own setup (instructions, limits, model).

New since 7 Nov: the mechanic can also sit beside the operator. Through Calvin, a coding agent can give Marvin a task, watch what he proposes, and approve or reject it, so Marvin's own tools can be tested from the terminal. This works only on a developer's machine, only on dev buildings on an allow-list, with a restore point taken first. In the product nothing changed: the Marvin service has no apply endpoint, and Approve is a button a person clicks in the browser.

Side by side

Calvin

the harness · for the person improving LumoCad

Who talks to it: an engineer, through a coding agent in the repository. The agent runs pnpm calvin <command>; each command runs inside the LumoCad tab the engineer has open, against the live state machines and stores, and answers in compact JSON (millimetres and degrees).

  • Sees the building you have open as data: floors, rooms, scans and poses, selection, dialogs, toasts, errors, screenshots.
  • Measures: which scan in a room disagrees with the others (a score called G1), how well two rooms line up (G4), and now how good a set of generated walls is (the wall benchmark).
  • Runs LumoCad's own tools (room autosort, floor autosort, fine alignment, boundary fitting) and agent-written lab scripts; edits to lab code apply without reloading the tab.
  • Talks to Marvin: marvin send, transcript, wait, approve, reject, budget.
  • Safety: writes only on dev buildings you list, one undo step per run, a checkpoint first, a session log and a read-only dashboard. It never commits or pushes by itself.

Marvin

the chat in LumoCad · for the person using LumoCad

Who talks to it: an architect or modeller, in the Assistant pane of the editor. Behind the pane is a Go service (the marvin repository) that keeps the chat history, runs the model and enforces the spending cap.

  • Answers questions about the building, navigates, explains plan problems.
  • Prepares changes as a preview ("Original" against "New"), with exact numbers.
  • Changes building data only, and only after a person clicks Approve. The model cannot approve its own proposal.
  • Can now write a restore point (create_building_backup) before risky work; those backups show as "Marvin" in the backup history.
  • After saving, he reads the server back and says "saved" or "unconfirmed". The editor's normal Undo restores it.
  • No access to code. Gets better through his tools (browser) and instructions (service); a tool change ships to both sides at once and bumps the protocol version.

How a tool travels from Calvin to Marvin

One loop, with a human at both gates. Teal is Calvin's lane, blue is Marvin's.

1

Spot a weak step

Someone sees a bad result, or a scorecard shows one: an outline that sits off the scan, a wall that does not match, a door in the wrong place.

2

Try and measure (Calvin)

On the building already open in the tab, Calvin runs the current tool, reads the score, changes the algorithm, runs again, and undoes what did not help. Each try takes seconds, because edits to lab code reach the next run without reloading the building. Since 7 Nov the same loop works for Marvin's tools: Calvin sends Marvin the request, waits for the proposal, and approves or rejects it on the dev building.

3

Put it into LumoCad

What worked stops being a lab script. Its logic moves into a normal LumoCad function with a test, so every button and every user gets it. This is also Arne's rule: use LumoCad's own functions, do not duplicate them as tools.

4

Marvin gets the tool

Marvin's tool is a thin wrapper that calls that function: a "plan" tool that prepares a candidate and a preview, and a "propose" tool that offers it for approval. The service's instructions are updated to say when to use it, and the protocol version is bumped in both repositories.

5

A user approves

In the chat the user sees Original and New, clicks Approve, the editor saves it through its normal path as one undo step, and Marvin reads the server back to confirm. A restore point can be written first with create_building_backup.

6

Score it on a gold building

A "gold" building is one a human has already finished and approved, so the right answer is known. Running a tool on a copy and comparing it with that answer turns "it looks better" into a number. For walls this exists since 8 Nov: a fixture is one floor as the generator reads it, pnpm wall-bench runs it through Marvin's path or the editor's path without a browser, and the scorecard reports coverage, open material, polygon IoU against reference walls and timings, with a baseline file to compare against. For outlines and openings it does not exist yet, and the gold buildings themselves (Hohental first) start on 9 Nov.

An example, in plain steps

A real finding, still open on 8 Nov. It is an illustration of how the loop would run; it has not been run end to end.

The finding

To draw a room outline from the scan, the editor has a button that uses the newer fitting method (v2, fit-line-intersections). Marvin's outline tool still uses the older one (v1, merged-edge-arrangement) by default (editorOps/service.ts:475 on agentic-dev), and leaves out the building's reference lines for slanted walls. So Marvin draws worse outlines than a person clicking the button.

1

Calvin measures both

On a room that looks wrong, Calvin runs pnpm calvin preview boundaries --method fit-line-intersections and the same with merged-edge-arrangement (nothing is applied), and compares how well each outline sits on the scan.

2

Calvin tunes it

If v2 with the reference lines wins on the rooms checked, the fix is small and lives in LumoCad: the function that runs the fit. The research of 7 Nov adds the missing piece, an objective outline score (how many scan points lie within 30 mm of the outline, and how much of the outline has support), so "wins" becomes a number.

3

Marvin follows

Marvin's plan_room_outline_fit is changed to use the same function with the same settings. His instructions do not change at all: he simply asks for a better outline and gets one. The user still sees the preview and clicks Approve. Calvin can run exactly this through pnpm calvin marvin send on a dev building before anyone else sees it.

4

Both are checked on the gold building

The score before and after goes on the scorecard. If it dropped on some building, Calvin sees it and goes again.

Glossary

Calvin
The harness: a control panel that lets a coding agent see and drive the LumoCad tab you have open, from the command line (pnpm calvin). It runs inside the Vite dev server; the browser part is a dev-only module.
Lab mode
Calvin's setting that applies code edits to the next run without reloading the building, so a try takes seconds.
Tool
One named action: for Calvin a lab script or a tool module; for Marvin a command the chat model may request, implemented in the browser and declared in the service.
Plan tool / propose tool
Marvin's two-step pattern: the plan tool prepares a candidate and a preview and changes nothing; the propose tool offers it for approval.
Protocol version
A number both halves of Marvin carry (31 on 8 Nov). The pane refuses a service with a different number, so a tool change ships to both repositories at once.
G1 / G4
Calvin's two sorting scores: G1 shows which scan in a room disagrees with the rest; G4 shows how well two rooms line up. Both measure how well scans overlap.
Wall benchmark
The first scorecard: one floor as the wall generator reads it, run without a browser through Marvin's or the editor's path, scored for coverage, open material, IoU against reference walls and timing.
Gold building
A finished, human-approved building kept as the right answer to measure tools against. Hohental is the first planned.
Restore point / backup
A snapshot of the whole building (sorting, CAD, roof, floor plans, stairs) that can be restored. Taken on every hand-in, by the Backups panel, or by Marvin's create_building_backup.
Allow-list
The file where the engineer lists which dev buildings Calvin may write to, including approving Marvin's proposals. Anything else is read-only.
Undo step
One Ctrl+Z. Both helpers are built so that one run is one undo step.
agentic-dev
The shared git branch of the platform repository where Marvin, Calvin and the agent work live since 8 Nov. Kept off development and main so hotfixes stay clean.
