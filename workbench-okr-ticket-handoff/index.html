Complete a ticket. Continue the same OKR.

A deliberate completion action now updates Notion and hands you directly to the next unblocked ticket in that key result.

Implemented 2 November 2026. The ordering is deterministic: keep unblocked in-progress work moving, otherwise choose the first available numbered step. It does not silently switch the user to a different OKR.

What changed

The ticket drawer in WorkHub now connects a completed ticket to the next piece of work, while keeping Notion as the official source of ticket status.

01

Mark done

The user explicitly confirms completion from a ticket panel. WorkHub writes the done status to Notion.

→
02

Re-read the plan

After Notion confirms the update, WorkHub refreshes the tickets and recalculates only that ticket’s key result.

→
03

Continue

The handoff names the next unblocked step and offers its ticket panel and a Workbench chat.

How it decides

Key result means the measurable outcome within an OKR. Tickets associated with it form its working plan.

  • It uses the ticket’s linked key result, rather than the global “Next up” ranking.
  • An unblocked in-progress ticket wins, so partly started work does not get abandoned.
  • Otherwise it selects the first unblocked open ticket in numbered-title order: 1., 2., 3..
  • If every remaining ticket is complete, in review, or blocked, it says so instead of proposing a misleading next task.

The global Next up screen remains useful for deciding between OKRs. This completion flow answers the narrower question: “What should I tackle next to continue this one?”

How to test

Press Mark done.Notion becomes the source of truth with the ticket marked done; WorkHub refreshes its view.
Use an OKR with numbered open tickets.A handoff shows the next unblocked ticket in that same key result.

Verified: root TypeScript check and three focused selection tests. The isolated Workbench shell rendered without browser errors. The production WorkHub build compiled this change, then stopped on pre-existing lint errors elsewhere in WorkHub.

What’s missing

The current data model allows a ticket to belong to multiple key results; this handoff follows the first linked key result, matching the existing ticket-panel convention. A future improvement could let users choose the target key result when a ticket genuinely contributes to more than one.

No real Notion write was exercised in test data, to avoid changing live work items. The action uses the same existing status-update function used by WorkHub’s accepted review proposals.
