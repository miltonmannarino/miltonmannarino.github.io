Steer while it works, hear the answer, keep each chat’s draft

Four changes to the chat screen in Workbench. You can now send a message while the agent is still working. Answers can be read aloud. Each chat keeps its own unsent text. And new chats start with the permission mode you last picked.

Status: built, type-checked, and covered by a new automated test for the queue. Nobody has tried it in the running app yet. The changes are in the working copy on main, next to unrelated work from another session (voice dictation and a Work Hub ticket rename), and nothing is committed.

What changed

Grouped by what you see on screen. Each part has a small drawing of that part of the app. The drawings are mock-ups, not screenshots.

01Queue messages while the agent works

Before: while the agent was busy, the send button turned into Stop. To redirect the agent you had to stop it or wait until it finished.

Now you can type and press Enter at any time. If the agent is busy, the message waits in a queue, shown in a strip above the message box. Messages go out one by one, in the order you sent them, each starting a new turn when the one before it ends. (A turn is one request plus everything the agent does to answer it.)

  • Send now is how you steer. It stops the current turn and sends this message next, ahead of anything else queued.
  • Edit takes a text-only message out of the queue and puts it back in the box. Messages with files or context have no Edit button, so nothing gets dropped silently.
  • × removes it.
  • Stop or a failed turn holds the queue instead of sending it. Held messages go out only when you click Send now.

The queue lives on the Workbench server, not in the browser tab. It works the same for Claude, Codex and local models, and keeps going if you switch chats or close the tab. A chat set to merge its worktree when it finishes now waits until the queue is empty before merging.

“Steering” here means stop, then send. The agent doesn’t receive your message in the middle of its current step. It is interrupted, and your message starts a fresh turn with the whole conversation behind it.

02Read answers aloud

You asked what text-to-speech would cost. Using the browser’s built-in voice costs nothing, needs no download or server, and works offline, so that’s what we built first.

Each finished answer has a Read button next to Copy. It turns into Stop while speaking. Only one answer reads at a time. Opening another chat stops it.

  • What it reads: only the final answer, the text after the agent’s last tool step. That’s the part Zen and Learning modes leave unfolded. The first version read every progress note in the turn (“Checking X…”, “Found it…”), which sounded like the whole chat. That was fixed the same day.
  • What it skips: code blocks, Markdown symbols (**, #, list bullets) and long web addresses (read as “link”). Tables are read row by row.
  • Voice: prefers a macOS “Premium” or “Enhanced” voice in your language if one is installed, otherwise the system default.
  • Long answers are spoken a sentence or two at a time, because Chrome cuts off speech after about 15 seconds.

03A message box per chat

Before: there was one message box for the whole app. Half a message typed in chat A was still sitting there when you opened chat B.

Now each chat keeps its own unsent text and attached files. When you switch chats, the box saves what’s in it under the chat you’re leaving and loads the other chat’s draft. The swap happens before the screen redraws, so the old text never flashes. The “new chat” screen keeps one draft per project.

A file still loading when you switch chats lands in the chat you added it to, not the one on screen. Work Hub context was already kept per chat and is unchanged.

04New chats start in the permission mode you last picked

The permission mode decides how much the agent may do without asking: Ask before edits, Accept edits, or Auto (a safety check approves routine actions).

If you set Auto in one chat, the next new chat now starts on Auto as well. There were two problems before:

  • A pick made inside an open chat applied to that chat only. It was saved for new chats only if you picked it on the empty new-chat screen.
  • The saved value shared a storage key (wb-mode) with the Coder / Zen / Learning view switch, so each setting kept erasing the other.

The permission mode now has its own key, wb-edit-mode, and every pick is saved. On first load it reads the old key, so an existing choice carries over. Changing the default never changes chats that already exist.

How to test

Reload Workbench first so the browser picks up the new build. Every check below is untested in the real app, so this list is the first hands-on try.

  1. Queue. Send a message that takes a while (for example “read every file in server/ and summarise it”). While it runs, type “and keep it under 100 words” and press Enter.
    Expected: a strip above the box shows it as Queued. When the turn ends, it is sent by itself and starts a new turn.
  2. Send now. Repeat, but click Send now on the queued message.
    Expected: the running turn ends as “Interrupted.” and your message goes out straight away.
  3. Held after Stop. Queue a message, then press Stop.
    Expected: the message stays in the strip marked Held and isn’t sent until you click Send now. × removes it. Edit puts the text back in the box.
  4. Read aloud. Under an answer that used tools, click Read.
    Expected: it reads only the final answer, not the progress notes and not the code blocks. The button becomes Stop. Switching chats stops the voice.
  5. Drafts per chat. Type “hello” in chat A, open chat B, type “world”, then go back to A.
    Expected: B started empty. A still says “hello”.
  6. Permission carry-over. In any open chat, set the permission chip to Auto, then click New chat.
    Expected: the new chat’s chip already says Auto. Switching between Coder and Zen doesn’t reset it.

Queue is lost when the server restarts

Queued messages live in the server’s memory, so a restart or rebuild drops them. Saving them with the chat is possible.

Queue only visible inside its chat

The sidebar doesn’t show that a chat has queued or held messages.

Real mid-turn steering

Send now interrupts and resends. Claude Code can take a message mid-turn without stopping, but how that behaves when driven this way isn’t documented. Worth trying only if interrupting feels too blunt.

Milton · decision

Drafts are lost on page reload

Per-chat drafts are kept in memory. Text could be saved in the browser so it survives a reload. Files are too big to save there.

Claude · follow-up

Dictation lands in the chat on screen

If you switch chats while dictation is still turning speech into text, the words go into the chat you’re now in.

Claude · follow-up

Read aloud: next steps

No auto-read when a turn ends (for example in Zen mode), and no voice or speed setting. If the browser voice feels robotic, a free local voice model (Kokoro or Piper) is the next step. A paid cloud voice only if quality really matters.

Read now uses only the final answer. Copy still includes the progress notes. Should it match?
