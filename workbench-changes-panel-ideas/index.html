The Changes panel, past the diff

Today the Changes panel works like an IDE's: red and green lines, comments on lines. But the person reading it didn't write that code. An agent did. So the reader asks different questions, and a line diff answers none of them well.

Below are four views, one per question, each shown as a mockup. My recommendation is to build the first two now, because Workbench already has all the data they need.

Status: proposal. None of this is built. The mockups use sample data based on a real Workbench commit (f9f4179, which made the message box row wrap and underlined the view tabs). Facts about what Workbench records today were checked in the code on 30 October 2026.

What Workbench knows that an IDE doesn't

An IDE or a terminal sees only the files. Workbench sits between you and the agent, so it already records five more things. Every view below is built from them.

  • The conversationYour messages and the agent's text, saved per chat in data/chats/.
  • Every edit, in orderClaude's Edit and Write calls with the old and new text, and Codex's file changes with their diffs. Both are already in the chat's event log.
  • A snapshot from the chat's startThe folder as it was, stored as refs/workbench/<chat>. It's what the "This chat" switch compares against.
  • The running app▶ Run starts the project's dev server and knows the address it prints.
  • Commands and their outputTest runs, type checks and builds the agent ran, with what they printed.

No AI in the main path. Each view is worked out from these records, so it gives the same answer every time and can't make things up. A small model is used in one place only, rarely, and its answers are kept so they're never paid for twice (see where a small model is worth it).

View 1

Did it do what I asked?

Group the diff by your requests instead of by file. Each group starts with what you asked, then shows the agent's own sentence from just before the edit, then the hunks (blocks of changed lines) that came out of it.

  • Your request on top. You check the change against what you wanted, not against a file list.
  • The agent's words, quoted. The caption is copied from the chat, so it isn't a summary that could be wrong.
  • Unexplained changes. Lines no edit call produced, for example ones changed by a shell command, a formatter or generated code, get their own group. These are often the ones worth checking.
  • Struggle marks. A line the agent wrote three times, or wrote and then reverted, gets an orange edge. That's where it was unsure.
How it's worked out
Computed: groups, unexplained lines, struggle marksQuoted from the chat: your message, the agent's sentenceAI: none

Replay the chat's edits in order, starting from the chat's snapshot. Tag each line in the final diff with the last edit that wrote it, and that edit with the turn and message it belongs to. Lines with no tag are "unexplained." Counting how many edits touched the same line gives the struggle marks.

View 2

What changed since I last looked?

Working with an agent is a loop: you review, you comment, the agent fixes, you review again. Today the second review shows the whole diff again, and you have to work out what moved. This view shows only what changed since your last review, which is called an interdiff (a diff between two versions of a diff).

  • Each comment gets a status. Under each comment you sent: the change that answered it. If its line didn't change, whether the agent's next answer mentions something on that line (a name or a value like 700px), with that part of the answer shown.
  • Seen marks that reset. Tick a hunk as seen. If the agent edits it again, the tick goes away and the hunk says so.
  • Everything else folded. Hunks you've already seen and that haven't changed stay hidden behind one link.
How it's worked out
Computed: since-review diff, seen marks, comment statusQuoted: the agent's next answerAI: none

When you send comments (or press a new "Mark reviewed" button), Workbench takes a second snapshot, the same way it takes the chat-start one. The view is the diff between that snapshot and now. Each comment already stores its line and that line's code (web/src/review.ts). Follow that line through the new edits: if it changed, the comment was answered by a change. If not, search the agent's next answer for the names and values on that line and show where they appear. Whether that answer really settles your point is left to you: judging it would take a model, and it isn't worth one here.

View 3

What does the user of the app see?

For most changes to a web app, what the diff means is "something on screen now looks or works differently." These two views show that directly, without asking you to read CSS.

  • Before and after. Workbench takes a screenshot of the running app when the turn starts and another when it ends. Drag to compare, or switch on "changed pixels" to outline what's different. For code with no screen, the same idea applies to output: the test count before and after, or an API response before and after.
  • The app with the changed parts lit up. This is the dependency idea from git flowdiff, but drawn onto the app instead of as a graph of files. Pick a changed file and every part of the screen it affects lights up, with the import chain that connects them.
How it's worked out
Computed: screenshots, pixel compare, import chains, CSS matchesAI, optional: names for unlabelled screen areas, once per component

Screenshots: Playwright (a tool that drives a browser from code) opens the address ▶ Run printed, at turn start and turn end, and compares the two images pixel by pixel.

Lit-up app: in development only, a small Vite plugin tags each element on the page with the component file that drew it. Workbench follows the imports from the changed file up to those components and outlines their elements. For CSS it's even simpler: it asks the page which elements the changed selectors match.

Names for screen areas: taken from the elements' own labels (headings, button and region labels) or a short list per project. Only where neither exists does a small model name the component, once, from its file; the name is kept until that file changes.

View 4

Where should I look first?

Agents often make large diffs where most lines are routine. This view sorts the routine from what needs a person, before you read a single line.

  • What kind of change it is. Each hunk is labelled formatting, rename, moved code, new code, changed logic, or deleted. Routine kinds are folded by default, so "142 lines changed" becomes "28 lines that need you."
  • Contract changes. Changes to things other code depends on: types in shared/protocol.ts (the messages between server and browser), exported functions, component props, environment variables, new packages. Both ends are shown, and an end that isn't in the diff is pointed out.
  • Risk flags. One line each, linked to the hunk: security code touched, tests removed or skipped, checks switched off (as any, @ts-ignore, errors caught and ignored), changed lines that no test runs.
How it's worked out
Computed: change kinds, contract changes, flagsAI: none

A parser (tree-sitter, the one many editors use) turns old and new code into their structure and compares that, not the text. This is how the difftastic tool spots renames and moved blocks. Contract changes come from exported names and a short list of contract files per project. Flags are a fixed list of patterns, plus test coverage compared against the changed lines when coverage is available. The reading order can come from git flowdiff: dependencies first.

Where a small model is worth it

The Changes panel refreshes after every step the agent takes, which can be dozens or hundreds of times an hour. The computed views can run on every refresh because they cost no tokens. A model only goes where it adds something computing can't, and never on refresh. Here is every place one could go, and the verdict.

SpotWithout a modelWhat a model would addVerdict
Title for each request (view 1)Your own messageA tidier titleNoYour words are already the best title.
The agent's caption (view 1)Quoted from the chatA summary of the editNoA quote can't be wrong; a summary can.
Did the agent answer my comment? (view 2)The line changed, or the next answer mentions what's on itJudges whether the answer settles the pointNot nowRevisit only as a button you press, and only if the rule misses often.
Names for screen areas (view 3b)Element labels, or a short list per projectNames components that have no labelYes, where labels are missingOnce per component, kept until its file changes. A few dozen calls for a whole project, then almost none.
"What does this change mean, in words?"NothingA plain explanation of the turnAlready existsLearning mode's card does this once per turn. Link to it instead of paying for a second one.
  • Never on refresh. At most once per finished turn, or only when you click.
  • Kept, not repeated. Each answer is stored under a fingerprint (hash) of its input, so the same input is never paid for twice.
  • Small input. One component's name and first lines, not the whole diff.
  • Smallest model, no tools. The same one-off Haiku call Workbench already uses for suggested replies and the commit message button.
  • Off for local-model chats, so their code stays on the machine, as with suggested replies and Learning cards today.
  • One switch in settings turns it off.

Recommended order

  1. Views 1 and 2 together: the diff as the story of the chat

    All the data is already recorded. They need nothing set up in your project, make no model calls, work for Claude, Codex and local models alike, and an IDE can't copy them because it doesn't have the conversation. Before building the layout, check the edit replay against about ten saved chats to see how often lines end up "unexplained."

  2. View 3b on Workbench itself

    The most direct answer to "show me what this diff means," and Workbench is a Vite + React app, so it's the easiest first target. If it holds up there, offer it to other projects.

  3. Views 3a and 4

    Screenshots once there's a good way to pick the page and its state. Triage once the first views show how much of a typical agent diff is routine.
